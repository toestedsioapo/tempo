## 4. Architecture decision records

### ADR 1 — Luxon, not Temporal (C12)

**Decision:** Use **Luxon** for all date-time work. Do not adopt Temporal.
**Why:** Temporal reached Stage 4 and ships in Node 26, but Luxon is mature, widely deployed, has the DST helpers Tempo needs, and keeps behaviour identical on the whole 24 + 26 runtime matrix without polyfills. (The earlier draft said “Stage 3”; that was out of date and is not the reason.)
**Consequences:** All `DateTime` construction goes through Luxon with an explicit zone. Core never imports `Temporal`. Luxon’s silent DST behaviour (gap → shifted forward; overlap → one offset, which for 3.7.2 is the later one) is **never relied on** for request times; Tempo detects both with a round-trip check (ADR 4). Revisit in a later ADR if Temporal support becomes universal.

### ADR 2 — Zone validation and abbreviations (C11)

**Decision:** *Ask, don’t guess.* Zones are validated **before** Luxon.
* A valid IANA id is accepted; `UTC` and `GMT` are accepted (they are not ambiguous).
* The abbreviations in SPEC §7 (`IST`, `CST`, `BST`, `EST`, `PST`, `MST`, `HST`) are **ambiguous** → `AMBIGUOUS_ZONE`, CLI **exit 3**, `details.options` from the table.
* Anything else that is not an IANA id → `INVALID_ZONE`, exit 2.
**Why:** Luxon accepts `IST`, `EST` and `PST` as valid zones and would silently resolve them. The fixed-offset legacy ids (`EST`, `MST`, `HST`) look like zones but are not what users mean.
**Consequences:** No interactive prompt (the CLI must be pipe- and agent-driveable). Core does not resolve abbreviations; it returns the error and the caller asks the human. The previous draft’s IST options (which included `America/New_York`) and its claim that `GMT` is ambiguous were wrong.

### ADR 3 — Injecting `now` (C8)

**Decision:** `options.now` is a **required** field in core, an **ISO-8601 UTC string** (`YYYY-MM-DDTHH:mm:ssZ`). Not an epoch number.
**Why:** One primitive type; `now` only gates candidate search (`IN_PAST`, `INSUFFICIENT_NOTICE`) and the search lower bound. DST context never depends on `now`.
**Consequences:** Tests pass fixed instants. The CLI supplies `--now` > `options.now` in the file > the real clock formatted as `…Z` (A-13). `INVALID_INPUT` for any other format (A-17).

### ADR 4 — DST policy (C10)

**Decision:** For the **request’s** wall times (`start`, `end`): a **nonexistent** time (spring-forward gap) and an **ambiguous** time (fall-back overlap) are **both rejected** with an explicit code (`DST_NONEXISTENT_LOCAL_TIME`, `DST_AMBIGUOUS_LOCAL_TIME`), CLI exit 2 (A-05). Detection is a Luxon round-trip check, plus a probe of the neighbouring offset for the overlap.
For **availability-rule boundaries** (A-07, needs approval): gap → forward, overlap → earlier occurrence, with an informational `DST_RULE_ADJUSTED` reason when it touches the request.
**Why:** “Never guess.” Silent shifting is the bug class Tempo exists to prevent.
**Consequences:** Callers resubmit with an unambiguous time. `details` contains everything needed (transition instant, both candidate instants). Fixtures cover US, EU, Australia/Sydney, Australia/Lord_Howe, and Asia/Manila (no DST), plus wrap-across-transition.

### ADR 5 — Interval algebra and ranking (C5, C6, C9)

**Decision:** Expand weekly rules to absolute UTC intervals owned by their start day; remove instances owned by a party’s blackout dates; merge touching/overlapping instances; “available” means contained in one merged interval. Counter-offers: absolute-distance ranking from the requested start on a 15-minute lattice (defaults), ties → earlier first, ≤ `maxSuggestions`.
**Why:** One interval algebra on UTC removes the whole class of “which day is this overnight shift” and DST bugs, and is easy to cross-check with an independent minute-by-minute oracle (E17).
**Consequences:** See SPEC §4 for exact semantics.

### ADR 6 — Errors are values (D13)

**Decision:** Core never throws for expected failures. It returns `{ ok: false, error: { code, message, details? } }`. The CLI maps `code` to an exit code.
**Why:** Keeps core pure and total; downstream (Deskhand MCP) can branch on `code` without try/catch. Property test INV-10 fuzzes arbitrary input for “never throws”.

### ADR 7 — CLI exit codes (D14)

**Decision:** Exit `0` whenever the computation succeeds. `--exit-code` maps `book` → `0`, `counter_offer` → `1`. Errors are always `2` (input) or `3` (ambiguous zone); `4` = internal error (A-12, needs approval).
**Why:** Separates “the tool worked” from “the answer was no”, which suits agents and shell pipelines alike. **Exit codes and JSON output shape are public API.**

### ADR 8 — `explain` (D15)

**Decision:** `explain` returns an `ExplainResult` with, per candidate and per participant, `{ participant, ruleMatched, pass, reasonCode }` using the stable `reasonCode` enum from SPEC §3.5–3.6.
**Why:** Traceable and machine-readable; the same trace powers the README demo and the agent skill.

## 5. Data flow

```
user / agent ──JSON (file or stdin)──▶ @marvinliem/tempo (CLI)
   parse args, read input, strip BOM
   resolve now:  --now  >  options.now in file  >  real clock
   ▼
@marvinliem/tempo-core  evaluate | suggest | explain      (pure)
   1 schema  2 zones  3 intervals  4 request wall times     ← first failure ⇒ { ok:false, error }
   expand rules → UTC instances → drop blackouts → merge
   gates (IN_PAST / INSUFFICIENT_NOTICE) → decision → candidate search → rank
   ▼
CLI: print (human, or JSON with --json) → exit code
        ok            → 0   (with --exit-code: book 0, counter_offer 1)
        INVALID_*, DST_* → 2
        AMBIGUOUS_ZONE   → 3
        INTERNAL_ERROR   → 4
```

## 6. Stability guarantees

* Exit codes (`0/1/2/3`, plus `4` once approved) and the JSON shapes of `NegotiationResult`, `ExplainResult` and `ErrorResult` are public API. A change needs a major bump (after 1.0; a minor bump with a CHANGELOG entry and migration note while on `0.x`).
* Output is deterministic: stable sort and tie-breaks everywhere.
* `ReasonCode` and `ErrorCode` are closed enums; adding a value is a minor change, removing or renaming one is breaking.
* No secrets in the repo; `.npmrc` and CI use GitHub OIDC for provenance, no tokens.
* `@marvinliem/tempo-core` is testable without mocks.
