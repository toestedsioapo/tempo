# Milestone 6 — Release v0.1.0: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** publish `@marvinliem/tempo-core` and `@marvinliem/tempo` at `0.1.0` to npm from GitHub Actions with provenance, tag `v0.1.0`, create the GitHub release, and prove the published packages work on Linux and Windows.

**Architecture:** no engine change. Work is package metadata, one changeset that produces `0.1.0` and the CHANGELOG, a real `release.yml` (manual dispatch, dry-run by default, approval-gated environment, npm trusted publishing over OIDC, plus a one-time bootstrap-token path for the first publish only, A-94) and a post-release verification workflow. Nothing is published until you approve the final task; every earlier task is reversible and runs on a branch.

**Tech Stack:** unchanged. Changesets 2.x (already installed), npm CLI >= 11.5.1 on the runner (Node 24 ships 11.x), `gh` CLI in Actions.

**Spec:** `ROADMAP.md` §M6; `ARCHITECTURE.md` §6 (stability, `0.x` rule); `ASSUMPTIONS.md` A-20, A-38, A-88, A-93, A-94, A-95; `CLAUDE.md` ("releases go through the GitHub Actions workflow with provenance", "Don't publish to npm locally"); npm docs "Trusted publishing for npm packages" (read 2026-11-06).

## Owner setup (you do these; nothing below can be done by me)

Publishing makes the **two packages and the repo's source code public**. Today `toestedsioapo/tempo` is **private** (`gh repo view` says `PRIVATE`). npm provenance is not generated for private repositories, so the repo has to become public **before** the real publish, and the tarballs (`dist/`, `schema/`, `fixtures/`) are world-readable on npm from then on. Versions cannot be re-used after `npm unpublish` windows close. Decide this consciously.

1. **npm account and scope.** Log in to npmjs.com as the owner of the `@marvinliem` scope (it must exist as a user or org you control). `pnpm check:names` (read-only) confirms the names are free or yours.
2. **Make the repo public** (GitHub → Settings → Danger zone → Change visibility) — only when you are ready; Task 5 checks it and refuses to publish while it is private. Review the history once more first (the M5 secret scan found nothing, `docs/reviews/m5-docs-match.md`).
3. **GitHub environment.** Repo → Settings → Environments → New environment named `release`; add yourself as **required reviewer**. This is the human gate in front of the publish job.
4. **Bootstrap token (first publish only, A-94).** npm needs a package to exist before a trusted publisher can be configured for it (npm docs prerequisite), so the first publish cannot use OIDC. Create one granular access token on npmjs.com: **read and write** on the `@marvinliem` scope (packages that do not exist yet cannot be picked one by one), **Bypass two-factor authentication** enabled (CI cannot answer a one-time password), **expires in 1 day**. Add it as an **environment secret named `NPM_BOOTSTRAP_TOKEN` on the `release` environment only** (not a repository secret), right before Task 5 Step 4. Do not put it in any file or chat.
5. **After v0.1.0 is live** (I tell you when `verify-release.yml` is green), you do these, in this order:
   1. For **both** `@marvinliem/tempo-core` and `@marvinliem/tempo` (npmjs.com, package, Settings, Trusted Publisher, GitHub Actions): organization or user `toestedsioapo`, repository `tempo`, workflow filename `release.yml`, environment name `release`. npm does not validate this when you save it; a typo shows up only as a failed publish.
   2. **Delete the token** on npmjs.com and **delete the `NPM_BOOTSTRAP_TOKEN` secret** on the GitHub `release` environment.
   3. On both packages enable **"Require two-factor authentication and disallow tokens"** (Settings, Publishing access).
   4. Tell me. Task 6 then removes the bootstrap branch from `release.yml`; until it is removed, CI is red on purpose (Task 3, Guard B).

   Steps 5.1 to 5.3 cannot be rehearsed: the first OIDC-only publish will be `0.1.1` or later, and Task 6 says so in `m6-release.md`.

## Global Constraints

- M1–M5 constraints still bind (strict TS, core pure, exit codes and JSON shape are public API, no secrets, Node `>=24`, CI on Node 24/26 × ubuntu/windows).
- **Nothing is published from a local machine.** No `npm publish`, `pnpm publish` or `changeset publish` outside `release.yml`.
- `release.yml` holds **no token value** and no `NPM_TOKEN` or `_authToken`. Auth is OIDC trusted publishing, with one exception (A-94): between the markers `# BOOTSTRAP-BEGIN` and `# BOOTSTRAP-END` a step may set `NODE_AUTH_TOKEN: ${{ secrets.NPM_BOOTSTRAP_TOKEN }}` (that exact secret name, nothing else) so the very first publish can create the packages. CFG-11 and the secret scan allow exactly that and nothing else. The bootstrap block is removed in Task 6 and two guards make leaving it in fail (Task 3).
- Both packages publish at exactly `0.1.0`; `CHANGELOG.md` files are generated by changesets, never hand-edited. On `main` the manifests stay at `0.0.0` with one pending `minor` changeset until the release run versions them (A-95).
- Publish order is core first, then cli (the cli depends on core).
- `pnpm check:names` stays read-only (GET only).

## Review Focus

Failure modes the tasks' main tests do not exercise, most likely first. Each line has its pinning step in the task named in brackets.

1. **Repo still private at publish time**: provenance cannot be generated and the publish fails after core may already be out. Expected: the workflow refuses to start publishing while the repo is private. [Task 3]
2. **`workspace:*` leaking into the cli tarball**: `@marvinliem/tempo-core: workspace:*` is uninstallable from npm. Expected: the packed cli manifest depends on `^0.1.0`. [Task 1]
3. **Tarball contents**: the cli must ship `dist/` and a runnable shebang bin and nothing else; core must ship `dist`, `schema`, `fixtures` and no `src/test/scripts`. Expected: installing both tarballs into an empty directory and running `tempo --version` prints `0.1.0` on Linux and Windows. [Tasks 1 and 3]
4. **Trusted-publisher misconfiguration** (owner, repo, workflow filename or environment name differs): fails only at publish and cannot be rehearsed. Expected: the rehearsal dry run proves everything *except* OIDC, and Task 5 says so before you approve. [Tasks 3 and 5]
5. **Partial publish** (core out, cli failed): re-running must not fail on the version that already exists, and the `v0.1.0` tag and release must exist only after **both** packages are on npm. Expected: tag and release steps run after publish and only on full success; `changeset publish` skips versions already on the registry. [Task 3]
6. **Bootstrap path left in after the first release** (a live token, or a path that silently skips OIDC for ever). Expected: the token has a 1-day expiry, `release.yml` fails when both packages already exist on npm and the secret is still set, and a repo test fails once `packages/cli/CHANGELOG.md` exists while `NPM_BOOTSTRAP_TOKEN` is still in `release.yml`. [Task 3, Task 6]
7. **Wrong version** (`0.2.0` or `0.1.1` instead of `0.1.0`). Expected: a test runs `changeset status` and requires `0.1.0` for both packages. [Task 2]
